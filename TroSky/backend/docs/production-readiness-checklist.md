# Production-readiness checklist

An honest status list, not an aspirational one — items are marked done
only where something in this codebase actually verifies them. Where a
CHANGELOG.md phase entry has more detail, it's linked rather than
repeated.

## Done

- [x] Argon2id password hashing, JWT access/refresh with rotation +
      reuse detection (a replayed refresh token revokes the whole
      session) — Phase 2.
- [x] Server-side, permission-based authorization on every protected
      route; cross-tenant resource access returns 404, never 403, so
      existence is never leaked — Phases 2–10, consistently.
- [x] No hardcoded secrets; the app refuses to boot in
      `APP_ENV=production` with a placeholder/short secret or
      `DEBUG=true` (`app/core/config.py`'s `_validate_production_safety`) — Phase 1.
- [x] GHS currency stored as `Decimal`/integer minor units, never
      `float`, throughout — Phase 1 convention, verified in every
      money-touching phase since.
- [x] Two independent, database-proven concurrency guarantees: a
      Postgres partial unique index (seat reservations, Phase 5) and
      row-locking (wallet balance, Phase 6), each backed by a genuine
      two-independent-session race test.
- [x] Idempotent webhook processing with signature verification and
      replay protection (Phase 6); idempotent booking/payment creation
      via `Idempotency-Key` (Phases 5–6).
- [x] Redis-backed rate limiting on registration, login, OTP,
      password reset, token refresh, payment initiation, QR
      validation, SOS, and location-publishing endpoints (Phase 1
      scaffolding, wired to its target endpoints in Phase 11).
- [x] Structured JSON logs with automatic sensitive-field redaction
      (`app/core/logging.py`, `app/core/config.py::redact_secrets`).
- [x] Prometheus metrics (`/metrics`) covering HTTP request/latency
      (generic, via `prometheus-fastapi-instrumentator`) plus
      domain-specific counters — payment events, webhook events,
      booking events, reservation expirations, GPS ingestion,
      WebSocket connections, notification delivery, SOS events — wired
      into their actual call sites as of Phase 11 (they existed as
      dead metric definitions since Phase 1 until then; see
      `CHANGELOG.md`'s Phase 11 entry).
- [x] OpenTelemetry tracing (OTLP/HTTP export), disabled by default,
      one flag (`OTEL_ENABLED`) to turn on.
- [x] Multi-stage, non-root (uid 1000) Docker image with a baked-in
      healthcheck (`Dockerfile`).
- [x] `docker-compose.yml`: full local stack (Postgres+PostGIS, Redis,
      MinIO, MailHog, API, worker, scheduler).
- [x] Kubernetes manifests: API (HPA 3–12 replicas, PDB, rolling
      update with zero unavailable capacity), Celery worker (HPA, PDB),
      Celery beat (deliberately single-replica, `Recreate` strategy),
      a dedicated migration Job (never run implicitly on pod startup),
      Ingress (TLS, WebSocket-appropriate timeouts), NetworkPolicy
      (default-deny + explicit allows) — `deployments/kubernetes/`.
- [x] CI pipeline: lint → typecheck → test (80% coverage gate) →
      dependency scan (Trivy over the resolved, pinned runtime
      dependencies; **blocking** on any fixable HIGH/CRITICAL finding) →
      container build & image scan (Trivy; still report-only until the
      base image is hardened) → environment-gated deploys, production
      requiring a manual approval via a protected GitHub Environment —
      `.github/workflows/ci.yml`.
- [x] Alembic migrations are hand-written (not autogenerated) and
      every one has been validated via `alembic upgrade head --sql` /
      `alembic downgrade head:base --sql` end to end — all eleven,
      chained, no gaps.

## Explicitly deferred (documented, not silently skipped)

Each of these already has a paper trail — this section just collects
them in one place rather than duplicating the reasoning again.

- Telecel Cash, AirtelTigo Money, and a generic card gateway have no
  verified real adapter (interface-complete skeletons that raise
  `ProviderError` rather than fabricate a request/response contract this
  codebase hasn't checked against a real vendor account) — see
  `app/providers/payments/unavailable.py` and the Phase 6 CHANGELOG entry.
- Google/Mapbox/HERE routing is likewise a verified-contract gap, not a
  documentation gap — ETA uses a local great-circle heuristic instead
  (`app/providers/maps/local.py`); see the Phase 8 entry.
- Automated mobile-money disbursement (payouts) is not wired up — MTN
  MoMo Collections has no payout endpoint of its own (that's the separate
  Disbursements product), so withdrawals are admin-confirmed rather than
  auto-paid. See `WithdrawalRequest`'s model docstring and the Phase 10
  entry.
- Trip cancellation does not cascade to cancelling its bookings/tickets
  (a Phase 4 gap that predates bookings entirely, never revisited since —
  see the Phase 7/9 entries for where it started actually mattering).
- No QR *image* generation server-side — the API returns the opaque
  signed token; rendering it is a client (mobile app) concern (Phase 7).
- Driver earnings are a flat, platform-wide percentage — no per-fleet
  negotiated-rate table (Phase 10).
- This test suite has not been executed against a real Postgres/Redis in
  *this* authoring environment (see every phase's CHANGELOG entry from
  Phase 2 onward) — `ruff`/`mypy`/collection are clean and every
  Postgres/Redis-dependent test skips (not fails) without them, repeatedly
  confirmed via full-suite runs, but "collects and skips cleanly" is not
  the same evidentiary bar as "passed against a real database." It runs
  for real in CI (`.github/workflows/ci.yml`) and via
  `docker compose up postgres redis && pytest`.

## Owed before an actual production launch (not yet started)

- **Legal/regulatory review** for Ghanaian data-protection obligations
  (Data Protection Act, 2012 (Act 843)) — this codebase implements
  technical controls (encryption in transit via TLS at the ingress,
  Argon2id hashing, structured audit-relevant logging, soft-deletes) but
  makes no compliance certification and has not been reviewed by counsel.
- A load test actually run against a real deployment (`tests/load/`
  provides the Locust scenarios; they have not been executed against a
  live environment from this authoring session for the same
  no-infrastructure reason noted above).
- Real vendor accounts/credentials for MTN MoMo production (sandbox
  credentials only get you sandbox — going live needs a merchant
  agreement with MTN), Firebase (a real service account), and any of the
  deferred providers above, if/when they're implemented.
- A populated `secret.example.yaml` → a real Secret, provisioned via an
  actual secret manager, not `kubectl apply -f` on a plaintext manifest.
- DNS, TLS certificate issuance (cert-manager `ClusterIssuer`), and the
  managed Postgres/Redis/S3 instances the Kubernetes manifests assume
  already exist — none of that infrastructure provisioning is in scope
  for this repository.
